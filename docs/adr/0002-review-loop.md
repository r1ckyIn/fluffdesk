# ADR 0002：审查循环

状态：已采纳（2026-10-28）。取代 CLAUDE.md 里 2026-10-28 早些时候那版"PR 流程"。

## 背景

前八个 PR 的审查是人盯着跑的。回看记录，问题有四类：

1. **修了不再审。** PR #6 的 code-review 回来十条，修了八条就准备合并，修复提交本身没人看过。
2. **审完又加提交。** PR #8 在两个审查之后加了发版脚本，差点带着没审过的代码合并。
3. **"顺手修"没有边界。** PR #8 的增量审查跑了四轮，每轮回来六到八条 medium，每轮都顺手修一批，
   每修一批就是一个新提交，又要再审。循环是靠规矩叫停的，不是收敛的。
4. **作者审自己。** `/test-review` 一直在写代码的那个上下文里跑；code-review 和 security-review
   虽然派了子代理，但哪些发现要修、哪些驳回，都是作者一个人定，high 也能一句话驳掉。

另外每一步都要人来推：说"再审一轮"、说"直到没有 high"、说"放进这个分支"、问"这些都做完了吗"。
我们要的是人只看输出，审和修都由 agent 做，收敛由规则保证。

参考了 Anthropic 的 Claude Code 团队 2026-10-15 那篇讲他们怎么做代码审查的文章，
取了这几点：开 PR 前先自证并贴证据；审查者必须是全新上下文；多个审查者找、独立的复核者判；
纯风格意见直接丢；安全审查能挡合并，每条要么修要么写明理由；人按风险看，不按谁写的看；
新提交之后要重新批。

## 决定

审查由一个项目 skill `/pr-review` 驱动，分五步，细则在 skill 里，这里记原则：

1. **先自证，再审查。** 工作区干净、门禁命令全绿、改动路径实际走过一遍，才开第一轮。
   证据进 PR 模板，没有证据的 PR 不开。页面改动的走查用 Claude in Chrome：agent 自己打开跑起来的
   应用，把每个流程点到尾，查控制台和网络请求，录 GIF，再用接口核对最终状态。测试证明代码按断言跑，
   走查证明东西真的能用，两个都要。走查只开本地 dev 和测试令牌，不碰生产和第三方登录；它不进 CI，
   走通的关键流程以后改写成 Playwright e2e 防回归。
2. **审查者全是新上下文。** test-review 在独立的子代理里跑，code-review 和 security-review
   本来就派子代理。作者只做分诊和修复，不做审查。
3. **分诊是机械规则，不是取舍。** 每条发现只能是四种结局之一：修、否决、记 TODO、丢弃。
   high 和 important 只能修，或者由一个独立复核子代理同意后否决；作者一个人否决不了 high。
   纯风格的意见丢弃不记。一轮的修复合成一个提交，这个提交就是下一轮的范围。
4. **收敛靠两条规则。** 停止条件：一轮里 code-review 没有新的 high 或 important，
   security 没有过滤后 ≥8 的保留项，test-review 没有必须改。轮数上限三轮（见下面的修订）。
   medium 和 low 在停止那一轮之后最多只准再修一次，那次修复只过一次补审（code-review，碰高风险
   路径 security 跟，碰测试路径 test-review 跟），之后的 medium 和 low 只记 TODO 不再改，否则"顺手修"
   永远停不下来。状态机细则以 skill 为准，这里不复述。
5. **第一轮审整个 PR，之后只审新提交。** 范围是 `<上一轮审到的提交>..HEAD`。
   审查之后加的任何提交都算新改动，包括文档。
6. **人只看输出。** 每轮一行摘要，最后一份按 PR 模板写的报告。人要做的只有三件：
   PR 太大时决定怎么拆；循环卡住（同一条修两次修不掉、修复又引入新的 high、三轮用完仍有 high）时来拍板；
   推分支和合并说一声"可以"。
7. **agent 不在循环里改自己的规矩。** 反复出现的同类发现写进 `docs/reviews/recurring-findings.md`，
   由人逐条决定写进哪条规矩。CLAUDE.md、skill、ADR、PR 模板在循环里只读，针对它们的发现同样进那个
   文件。会改变 agent 行为的东西要过人，这是唯一不交给 agent 的决定。例外是 PR 的交付物本身就是
   规则（人明确要求改流程）：那时规则文本的发现照常分诊修复，提交正文注明。
8. **风险分级只改变审查强度和人看的重点，不改变人要不要参与。** 高风险路径（鉴权、路由、
   提示词和工具定义、上限、SSRF 守卫、迁移、CI 和发版、评分逻辑、skill）code-review 用 high，
   security 必跑，报告里列出来让人重点看；低风险（文档、设计 token、纯测试）code-review 用
   medium，security 不涉及就跳过。

## 修订（2026-10-28 晚，PR #9 跑完之后）

第一次按这个循环跑的是 PR #9：8 轮完整循环加 1 次只审 README 文档提交的补审（2 条 low），修 55 条，否决 1，
TODO 12，熔断一次。八轮里 security 零发现，test-review 后六轮没有必须改；code-review 每轮
10 / 9 / 8 / 6 / 7 / 8 / 6 / 5 条，没有收敛到零。
两条触发熔断的 important 都是修复自己引进的。据此改四条：

1. **轮数上限三轮**，每个修复提交都被下一轮或一次补审审到；第三轮的修复补审后仍有 high 或 important 就交给人。第 1 轮抓到了全部要紧的，
   三轮之后还收敛不了，问题在修法或 PR 规模，不在轮数。原来"不设上限"那条删掉。
2. **先复现再修**。审查者的发现是线索不是事实：后端先写会红的测试，前端写复现步骤并点出来；复现不了的否决，
   记进 `docs/reviews/dismissed.md`，下一轮审查者带着它。#9 里我八轮只否决了一条，其余照单全修，
   等于把审查者的话当事实执行。
3. **PR 规模是进入条件**。diff 超过 40 个文件或 1500 行先拆。#9 把五样东西塞进一个 PR，第 1 轮就该拆。
4. **同一文件连续两轮出现在修复提交里，第三轮不许再打补丁**，要么结构性改一次，要么 medium 以下记 TODO；剩下 high 或 important 又不做结构性改法就是卡住，交给人。
   #9 的 BookingDetail 连改五轮，第 8 轮审查者才点出结构性解法（key 放到调用点），早该在第 2 轮做。

## 不做什么

- 不用轮数上限代替停止条件：上限到了仍有 high 或 important 是交给人，不是吞掉。
- 不让作者在主上下文里审查。同一个上下文写的代码它自己看不出问题。
- 不在停止之后"顺手"改代码。要改就是新一轮。
- 不把审查发现直接当事实。code-review 的 PLAUSIBLE 和 security 的候选都要过复核才算数。
- 不让人逐行读 diff。人看证据表、风险等级和审查记录。

## 强制力

和 ADR 0001 一样递减：CI 门禁 > `CLAUDE.md`（每个会话加载）> `/pr-review` skill（被调用时加载）
> PR 模板 > 本文。改流程要同步改 CLAUDE.md 的"PR 流程"和 skill。
