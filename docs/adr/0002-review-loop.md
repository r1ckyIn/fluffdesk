# ADR 0002：审查循环

状态：已采纳（2026-10-28）。取代 CLAUDE.md 里 2026-10-28 早些时候那版"PR 流程"。

## 背景

前八个 PR 的审查是人盯着跑的。回看记录，问题有四类：

1. **修了不再审。** PR #6 的 code-review 回来十条，修了八条就准备合并，修复提交本身没人看过。
2. **审完又加提交。** PR #8 在两个审查之后加了发版脚本，差点带着没审过的代码合并。
3. **"顺手修"没有边界。** PR #8 的增量审查跑了四轮，每轮回来六到八条 medium，每轮都顺手修一批，
   每修一批就是一个新提交，又要再审。循环是靠规矩叫停的，不是收敛的。
4. **作者审自己。** `/test-review` 一直在写代码的那个上下文里跑；code-review 和 security-review
   虽然派了子代理，但哪些发现要修、哪些驳回，都是作者一个人定，high 也能一句话驳掉。

另外每一步都要人来推：说"再审一轮"、说"直到没有 high"、说"放进这个分支"、问"这些都做完了吗"。
我们要的是人只看输出，审和修都由 agent 做，收敛由规则保证。

参考了 Anthropic 的 Claude Code 团队 2026-10-15 那篇讲他们怎么做代码审查的文章，
取了这几点：开 PR 前先自证并贴证据；审查者必须是全新上下文；多个审查者找、独立的复核者判；
纯风格意见直接丢；安全审查能挡合并，每条要么修要么写明理由；人按风险看，不按谁写的看；
新提交之后要重新批。

## 决定

审查由一个项目 skill `/pr-review` 驱动，分五步，细则在 skill 里，这里记原则：

1. **先自证，再审查。** 工作区干净、门禁命令全绿、改动路径实际走过一遍，才开第一轮。
   证据进 PR 模板，没有证据的 PR 不开。
2. **审查者全是新上下文。** test-review 在独立的子代理里跑，code-review 和 security-review
   本来就派子代理。作者只做分诊和修复，不做审查。
3. **分诊是机械规则，不是取舍。** 每条发现只能是四种结局之一：修、否决、记 TODO、丢弃。
   high 和 important 只能修，或者由一个独立复核子代理同意后否决；作者一个人否决不了 high。
   纯风格的意见丢弃不记。一轮的修复合成一个提交，这个提交就是下一轮的范围。
4. **收敛靠两条规则。** 停止条件：一轮里 code-review 没有新的 high 或 important，
   security 没有过滤后 ≥8 的保留项，test-review 没有必须改。轮数不设上限。
   medium 和 low 在停止那一轮之后最多只准再修一次，那次修复只过一轮 code-review，之后的
   medium 和 low 只记 TODO 不再改，否则"顺手修"永远停不下来。
5. **第一轮审整个 PR，之后只审新提交。** 范围是 `<上一轮审到的提交>..HEAD`。
   审查之后加的任何提交都算新改动，包括文档。
6. **人只看输出。** 每轮一行摘要，最后一份按 PR 模板写的报告。人要做的只有两件：
   推分支和合并说一声"可以"；循环卡住（同一条修两次修不掉、修复又引入新的 high）时来拍板。
7. **风险分级只改变审查强度和人看的重点，不改变人要不要参与。** 高风险路径（鉴权、路由、
   提示词和工具定义、上限、SSRF 守卫、迁移、CI 和发版、评分逻辑、skill）code-review 用 high，
   security 必跑，报告里列出来让人重点看；低风险（文档、设计 token、纯测试）code-review 用
   medium，security 不涉及就跳过。

## 不做什么

- 不用轮数上限代替停止条件。上限只会让最后一轮的发现被吞掉。
- 不让作者在主上下文里审查。同一个上下文写的代码它自己看不出问题。
- 不在停止之后"顺手"改代码。要改就是新一轮。
- 不把审查发现直接当事实。code-review 的 PLAUSIBLE 和 security 的候选都要过复核才算数。
- 不让人逐行读 diff。人看证据表、风险等级和审查记录。

## 强制力

和 ADR 0001 一样递减：CI 门禁 > `CLAUDE.md`（每个会话加载）> `/pr-review` skill（被调用时加载）
> PR 模板 > 本文。改流程要同步改 CLAUDE.md 的"PR 流程"和 skill。
